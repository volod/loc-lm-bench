# Acquired-Corpus Projection

Status: **PARTLY IMPLEMENTED data contract**. It describes the shape an upstream acquisition
service renders into, and what this project reads back from it. Every sidecar field below is read
at ingestion today and carried into the manifest item, chunk metadata, and the gold-set provenance
record ([acquired-corpus provenance](../impl/current/data-prep/acquired-provenance.md)). The
round-trip fixture now checks the projection shape; what is still open in
[the plan](../impl/plan.md) is ACTING on the values through revision semantics, the corpus-version
binding, and the redistribution gate. The capability itself, its boundary, and why the seam is
shaped this way are in
[the spec section that owns it](spec.md#corpus-provenance-and-acquisition-boundary).

This is the sibling of the [external-service draft contract](external-draft-contract.md). That one
governs artifacts an operator obtains by hand from a chat provider; this one governs a corpus a
machine hands over on an ongoing basis.

## Why a projection rather than a format

A file format agreed between two repositories is a point-to-point mapping. It works until a third
consumer appears, and then there are three mappings to keep in step -- and the moment one consumer
needs a field, every other consumer's parser is in the blast radius.

A projection inverts that. The producing side keeps ONE object model of its own domain and renders a
view of it per consumer. The consequences that matter here:

- Nothing in this project needs to know how acquisition works, only what a projected document
  carries.
- Nothing in the producing service needs to know this project's schema, only how to render into it.
- A field this project needs later is added to ITS projection. That is neither a change to the
  producer's model nor a schema change here.
- A second producer conforms by rendering the same projection. There is no bilateral agreement to
  renegotiate, and no producer-specific branch in this project's ingest.

## What the producing side is assumed to model

This project does not require a particular implementation upstream, but the projection only makes
sense if the producer distinguishes a few things. The vocabulary below is aligned to the W3C
provenance model so it stays readable outside either repository.

| Object | Meaning |
| --- | --- |
| `Source` | A publisher or registry |
| `Determination` | A recorded judgement of a Source's terms -- retention, processing, redistribution -- with its date |
| `AcquisitionRun` | One batch of fetching |
| `Capture` | An immutable observation of a Source at a moment: target URI, capture time, payload digest |
| `Derivation` | The step turning a Capture into a Document |
| `Document` | Normalized immutable text with a content-derived identity |
| `Span` | A character range within a Document |
| `Operator` | The person accountable for a Determination |

The links this project depends on: a `Document` was derived from a `Capture`, a `Capture` was
generated by an `AcquisitionRun` and attributed to a `Source`, a `Document` may be a revision of an
earlier `Document`, and a `Span` sits within a `Document`. Everything else in a producer's model is
its own business.

## Directory layout

```text
<corpus-root>/
  <doc_id>.md                 normalized document text, UTF-8
  <doc_id>.metadata.json      per-document sidecar
```

One text file and one sidecar per document. No nesting and no index file: this project's own
ingestion (`llb ingest-corpus`) produces the manifest and corpus fingerprint it needs, and an
index rendered upstream would be a second source of truth for the same facts.

The sidecar name is the existing `<source>.metadata.json` convention read by
`src/llb/prep/corpus/governance.py`, so a projected corpus is a legal input to `llb ingest-corpus`
before any task below lands.

`doc_id` is derived from the `Capture` payload digest and the `Derivation` normalization version.
Two consequences follow, and both are load-bearing on this side: re-deriving from one Capture always
yields the same `doc_id` and byte-identical text, and a changed upstream yields a DIFFERENT `doc_id`
rather than a rewrite of an existing one.

## Sidecar fields

The operator-lane fields, and what each is rendered from. These predate the projection and a
staged corpus carries them whether or not an acquisition service produced it:

| Sidecar field | Rendered from | Note |
| --- | --- | --- |
| `language` | `Document.language` | measured from script content rather than assumed from the source |
| `version` | `Derivation.normalization_version` | one of the two ordering fields the conflict audit reads |
| `effective_date` | publication date carried on the `Capture` | absent when the source states none; the other ordering field |
| `ingestion_time` | left unset | this project sets it at its own ingest, and it is a local event |
| `source_system` | `AcquisitionRun` identity | never `local`, which is this project's default for operator directories |
| `acl_label` | `Determination.access_class` | who may READ the document inside a run |

The fields the projection adds. All seven are read from the sidecar (and from the sidecar only --
front matter stays the operator-authored lane), and a document supplying none of them records their
absence explicitly rather than omitting the keys:

| Sidecar field | Rendered from | What it answers here |
| --- | --- | --- |
| `source_uri` | `Capture.target_uri` | which URI the text came from |
| `capture_time` | `Capture.capture_time` | when the source was observed, as distinct from `ingestion_time` |
| `capture_id` | `Capture` identity | resolvable in the producer's capture store |
| `payload_digest` | `Capture.payload_digest` | digest of the CAPTURED bytes, not of the local staged file |
| `licence` | `Determination.redistribution_class` | whether the material may leave the host |
| `acquisition_run_id` | `AcquisitionRun` identity | which run produced this corpus version |
| `revision_of` | the earlier `Document` identity, when this document revises one | which document this supersedes |

Extra fields are additive by construction: none of them alters document text, a `doc_id`, or a
character offset, so adding one can never move a label. A consumer that does not know a field
ignores it, and a corpus that carries none of them ingests exactly as an operator's own directory
does. Widening the field set a consumer records does change that consumer's own corpus fingerprint,
which costs a store rebuild on its side and nothing on the producer's -- this side has taken that
cost once, for all seven at once.

## Invariants

Both sides depend on these, and each one is a rule about what must NOT happen:

- **Document text is immutable.** Gold spans are character offsets into it. A producer that
  normalizes a document differently emits a new `doc_id`; it never rewrites text under an existing
  one.
- **Character offsets are the join key.** Chunk identities are internal to this project and never
  cross the seam in either direction.
- **The producer does not chunk.** It renders a document and stops. Chunking is a retrieval decision
  measured on this side and re-taken whenever the chunker changes.
- **Provenance is additive.** No projected field alters document text or character offsets, so
  adding one can never move a label.
- **Captures are not redistributed.** Only digests, URIs, offsets and terms leave the machine.
  `licence` is what makes that enforceable on this side; see
  [the data egress boundary](spec.md#data-egress-boundary).

## What this side guarantees back

The contract is not one-directional. In exchange, this project:

- treats a document whose `source_system` names an acquisition run as append-only: a revision
  becomes a new version and the superseded version is retained, so labels written against the old
  text keep resolving;
- records the acquisition run alongside the corpus fingerprint in a gold-set bundle, so a bundle
  names the corpus version its spans are valid against;
- refuses, rather than filters, an export carrying material whose `licence` forbids redistribution;
- never claims a licence determination of its own. The producing side decides; this side enforces
  what it was told.

## Conformance

Conformance is checked by a committed round-trip fixture rather than by prose. A small corpus in the
projection shape lives in this repository's fixtures, ingests with every document reported `ok`, and
a deliberate rename of any projected field name fails the check instead of passing silently. Both
sides exercise their half; a disagreement is a failing check on the side that drifted, and where the
two sides disagree about the projection, the CONSUMING side's reading wins, because it is the one
already shipped against.
